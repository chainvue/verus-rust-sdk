# Example specs

Ready-to-run input for the examples that read a JSON specification, so every
command in [the examples index](../README.md) is one line rather than a schema
to fill in.

```sh
cargo run -q -p verus-sdk --example send < crates/verus-sdk/examples/specs/send.json
```

`../../tests/example_specs.rs` runs every file here. A spec is exactly the kind
of thing that rots unnoticed — nothing compiles it, nothing imports it, and a
field rename leaves it valid JSON and wrong.

## Where the data comes from

| Spec | Source |
|---|---|
| `send.json` | vector 0 of `fixtures/transparent/vectors.json` — so its txid is one checked byte-for-byte against the TypeScript SDK |
| `send_token.json` | the token vector of the same file, with the field names this example uses |
| `read_notes.json` | `fixtures/daemon/shielded_memo.json` — the z→z from `PROVEN.md`, decrypted with its viewing key |
| `register_id.step1.json` | written by hand; the only input a first step needs |
| `register_id.step2.json` | generated by running step 1 once and recording its salt and commitment |
| `update_id.json`, `revoke_id.json` | generated by running step 2 and taking the identity output out of the transaction it built |
| `keygen_shielded.json` | 64 zero bytes: an obviously fake seed |
| `shield.json` | written by hand, paying the address `keygen_shielded.json` derives |

The WIF throughout is `UusoQ…`, which already appears in this repository's
public fixtures and holds nothing. The txids are `aaaa…`, `bbbb…`, `cccc…`:
placeholders, because an offline builder never checks whether an outpoint
exists — that is the node's job, and the point of being able to build without
one.

## Regenerating the identity chain

`register_id.step2.json` carries a salt from one recorded run of step 1, and
`update_id.json` / `revoke_id.json` carry the identity that step 2 built. They
are only consistent with each other, not with a step 1 you run now — step 1
draws a fresh random salt every time, and it exists nowhere else.

So if the registration format changes, regenerate all three together: run step
1, copy its `salt` and its commitment output into step 2, run step 2, and take
the identity output (the one whose script starts `4704`) into the other two.

Two constraints that are easy to lose while doing it:

* Step 2 must point its `recovery_authority` **somewhere other than the
  identity itself**, or `revoke_id.json` stops working — an identity that is its
  own recovery authority can never be revoked, because nobody could then recover
  it, and the builder refuses first. (The spec points `revocation_authority`
  elsewhere too, which is realistic but not what the refusal turns on.)
* The identity's `primary_addresses` must contain the address of the `wif` used
  by `update_id.json`, or it fails with `NotAPrimaryAddress`. That refusal is
  correct: an update must be signed by the identity's own authority.
